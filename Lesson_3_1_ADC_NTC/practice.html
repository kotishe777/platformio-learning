Аналогові сигнали: як мікроконтролер
перетворює напругу з датчика на число?

Практика на ESP32 у чистому ESP-IDF v5.5.4 (Espressif-IDE / Eclipse), без Arduino-обгортки. Фоторезистор (LDR) у дільнику напруги, АЦП через новий API esp_adc/adc_oneshot.h. Пройдемо весь шлях від «сирого» числа 0–4095 до вольтів і назад до фізичної величини: дискретизацію, атенюацію входу, квантування, оверсемплінг і заводське калібрування через adc_cali. У фіналі зберемо неблокуючий світловий сигналізатор з гістерезисом на esp_timer_get_time() — без жодного блокуючого vTaskDelay() у логіці вимірювання.

Ідея всього уроку одним реченням
АЦП — це міст між аналоговим і цифровим світом. Фоторезистор дає неперервну напругу, яка плавно змінюється від темряви до світла. Мікроконтролер же розуміє лише числа. Сьогодні відчуємо руками всі три етапи цього перетворення: дискретизацію (коли читаємо), квантування (на скільки рівнів ділимо напругу) і кодування (яке число зрештою отримує програма) — працюючи безпосередньо з апаратним API ESP-IDF, без жодних прихованих Arduino-обгорток.
Як зібрати дільник напруги з фоторезистором
Схема: 3.3V → LDR → (вузол з ADC-піном) → резистор 10 кОм → GND. Це класичний дільник напруги: коли світло яскравіше, опір LDR падає, і напруга у вузлі (яку читає АЦП) зростає. У темряві — навпаки, опір LDR росте, і напруга у вузлі падає ближче до 0V. Резистор 10 кОм — це «пара» для типового LDR (темновий опір — сотні кОм, на світлі — одиниці кОм).
Як під'єднати світлодіод (щоб не спалити)
Світлодіод має полярність: довша ніжка — анод (+), коротша — катод (−). Схема: GPIO → резистор 220–330 Ом → анод LED → катод → GND. Резистор обов'язковий. Струм малий (~5–10 мА), тож LED можна живити прямо з піна.

Чому саме так зручно
Дільник напруги — найпростіший спосіб перетворити зміну опору на зміну напруги, яку вже вміє читати АЦП. Світлодіод у фіналі загориться, коли стане темно — наочний доказ того, що ланцюжок «фізична величина → напруга → число → рішення програми» працює наскрізь.

Перший adc_oneshot_read(): від напруги до числаСИРЕ ЗНАЧЕННЯ 0–4095 · 12-БІТНИЙ АЦП
Почнемо з мінімального коду на «чистому» ESP-IDF: ініціалізуємо блок АЦП, читаємо напругу на вузлі дільника й друкуємо число. Побачимо, що це число само по собі ще нічого не «розуміє» — його треба інтерпретувати.
Крок 1adc_oneshot_read(): дивимось на «сире» число АЦП⏱ 15 хв
Мета

Прочитати аналоговий вузол і надрукувати число від 0 до 4095 (12-бітний АЦП за замовчуванням). Перекрити датчик рукою і посвітити на нього ліхтариком телефону — побачити, як число реагує.

Код · main/main.c
// Модуль 3.1 — Крок 1: перше читання АЦП (ESP-IDF, adc_oneshot API)
#include <stdio.h>
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "esp_adc/adc_oneshot.h"     // новий (IDF v5.x) API одноразових замірів АЦП
#include "esp_log.h"

#define ADC_UNIT     ADC_UNIT_1        // АЦП1 — не конфліктує з Wi-Fi
#define ADC_CHANNEL  ADC_CHANNEL_6     // GPIO34 на класичному ESP32 = ADC1_CHANNEL_6
static const char *TAG = "ADC_LAB";

void app_main(void)
{
    adc_oneshot_unit_handle_t adc1_handle;               // хендл блока АЦП1 — потрібен для всіх подальших викликів
    adc_oneshot_unit_init_cfg_t init_config = {
        .unit_id = ADC_UNIT,
    };
    adc_oneshot_new_unit(&init_config, &adc1_handle);    // реєструємо блок АЦП1

    adc_oneshot_chan_cfg_t chan_config = {
        .bitwidth = ADC_BITWIDTH_DEFAULT,                // типова роздільна здатність (12 біт на класичному ESP32)
        .atten    = ADC_ATTEN_DB_12,                      // дозволяє читати повний діапазон ~0-3.3В (детально — Крок 2)
    };
    adc_oneshot_config_channel(adc1_handle, ADC_CHANNEL, &chan_config);

    while (1) {
        int raw = 0;
        adc_oneshot_read(adc1_handle, ADC_CHANNEL, &raw); // ОДИН замір: дискретизація + квантування + кодування за один виклик
        ESP_LOGI(TAG, "Сире значення: %d", raw);

        vTaskDelay(pdMS_TO_TICKS(200));                   // пауза 200 мс — щоб монітор встигав, і задача не займала весь CPU
    }
}
Що спостерігаємо
У світлій кімнаті число велике (ближче до 4095), якщо прикрити датчик рукою — падає (ближче до 0). Значення трохи «тремтить» навіть при незмінному світлі — це шум АЦП і живлення, з ним попрацюємо в Кроці 5.
Що насправді відбувається всередині adc_oneshot_read()
Виклик adc_oneshot_read() запускає повний цикл АЦП: дискретизація (АЦП фіксує напругу саме в цю мить), квантування (порівнює її з 4096 рівнями між 0 і опорною напругою) і кодування (повертає ціле число — індекс найближчого рівня). Усе це відбувається апаратно, за одиниці мікросекунд, всередині SAR-АЦП (Successive Approximation Register) — послідовних порівнянь, що звужують діапазон удвічі на кожному кроці.
Чому ініціалізація тут явна, а не прихована
В Arduino-обгортці виклик analogRead() сам ховає від тебе adc_oneshot_new_unit() і adc_oneshot_config_channel() — вони виконуються автоматично один раз при першому зверненні. У «чистому» ESP-IDF ці кроки треба зробити явно, зате ти точно бачиш і контролюєш кожен параметр АЦП: юніт, канал, розрядність, атенюацію.

Специфіка ESP-IDF, якої немає в Arduino-обгортці «з коробки»: треба явно вказати, у якому діапазоні вольтів очікувати сигнал. Розберемо, чому і що станеться, якщо забути.
Крок 2Що станеться без правильної атенюації⏱ 10 хв
Мета

Навмисно поставити занадто малу атенюацію (ADC_ATTEN_DB_0) і побачити, що показник «впирається в стелю» задовго до повного освітлення датчика — сигнал обрізається.

Код · main/main.c (фрагмент, що змінюємо)
// Модуль 3.1 — Крок 2: занадто мала атенюація — сигнал «обрізається»
adc_oneshot_chan_cfg_t chan_config = {
    .bitwidth = ADC_BITWIDTH_DEFAULT,
    .atten    = ADC_ATTEN_DB_0,       // ← навмисна помилка: діапазон входу лише 0-1.1В!
};
adc_oneshot_config_channel(adc1_handle, ADC_CHANNEL, &chan_config);
Що спостерігаємо
Навіть у звичайній кімнаті (не яскраве світло) значення швидко впирається в 4095 і далі не росте, хоча реальна напруга на вузлі ще росте разом із освітленням. Це «стеля» АЦП при ADC_ATTEN_DB_0 — усе, що вище ~1.1В, читається як однаковий максимум.

Звідки береться ця «стеля»
Внутрішній АЦП ESP32 фізично здатен коректно вимірювати напругу лише в діапазоні приблизно 0–1.1 В — це його «рідний» робочий діапазон. Наш дільник напруги видає напругу до 3.3 В. Атенюатор — апаратний блок перед самим АЦП, який пропорційно зменшує вхідну напругу перед вимірюванням, а результат перераховується назад. Це як переставити лінійку — та сама кількість поділок (4096), але тепер вони покривають ширший діапазон реальної напруги. Постав назад ADC_ATTEN_DB_12, і показник знову зможе рости аж до реального максимуму освітленості.
Побічна ціна ширшого діапазону
Що більше атенюація, то трохи менша точність біля нижньої межі діапазону — те саме число поділок (4096) розтягнуто на ширший діапазон вольтів, тож кожна поділка «важить» більше мілівольт. Це прямий наслідок формули LSB = Vref / 2^N з лекції — тут «Vref» фактично розширюється атенюацією.

Дискретизація: як часто питати датчикЧАСТОТА ДИСКРЕТИЗАЦІЇ · ТЕОРЕМА NYQUIST · АЛІЗИНГ
Дискретизація вирішує проблему часу: коли саме «фотографувати» сигнал. Побачимо, що занадто рідкі знімки можуть пропустити або спотворити швидку подію.
Крок 3Що буде, якщо читати датчик надто рідко⏱ 15 хв
Мета

Імітувати швидку зміну освітленості — швидко махати рукою над LDR — і подивитись, як картина в логах змінюється залежно від частоти дискретизації (vTaskDelay() у циклі).

Код · main/main.c (цикл читання)
// Модуль 3.1 — Крок 3: вплив частоти дискретизації
while (1) {
    int raw = 0;
    adc_oneshot_read(adc1_handle, ADC_CHANNEL, &raw);
    ESP_LOGI(TAG, "raw=%d", raw);

    // --- спробуй три значення затримки по черзі ---
    vTaskDelay(pdMS_TO_TICKS(20));       // ① часта дискретизація (~50 Гц) — бачимо кожен «змах» чітко
    // vTaskDelay(pdMS_TO_TICKS(200));   // ② помірна (~5 Гц) — «змахи» вже розмиті
    // vTaskDelay(pdMS_TO_TICKS(1000));  // ③ рідка (~1 Гц) — швидкі змахи майже не видно, або видно неправильно
}
Експеримент: три швидкості дискретизації
Залий із vTaskDelay(pdMS_TO_TICKS(20)) — швидко махай рукою над датчиком 5–6 разів за секунду. У логу видно чіткі «провали» значення. Тепер розкоментуй варіант з 1000 мс — і повтори той самий рух. Провали або зникають, або лог показує геть іншу, повільнішу картину, ніж твій справжній рух руки. Це наслідок надто рідкої дискретизації.
Теорема Nyquist на практиці
Щоб коректно відновити сигнал з максимальною частотою f_max, частота дискретизації має бути f_s ≥ 2 × f_max. Твій рух руки — це сигнал із частотою приблизно 1–3 Гц (один «змах» за 0.3–1 с). Отже, vTaskDelay(20) (≈50 Гц) дає величезний запас, а vTaskDelay(1000) (1 Гц) — це вже межа або порушення теореми: швидкі змахи «зливаються» або спотворюються — виникає алізинг, коли швидка зміна маскується під повільну.
Коли це критично в реальних проєктах
Для повільних величин (температура кімнати, рівень освітленості за вікном) навіть vTaskDelay(1000) цілком достатньо. Але для вібрації, звуку чи швидких перехідних процесів занизька частота дискретизації дає хибні дані, які виглядають правдоподібно — і саме тому небезпечна: помилку важко помітити без спеціального обладнання.

Лінійка доступних значень ADC_BITWIDTH_x залежить від конкретного чипа ESP32 — звіряй із adc_types.h свого SDK; на класичному ESP32 діапазон ADC_BITWIDTH_9 … ADC_BITWIDTH_12.
Що спостерігаємо
На 12 бітах число змінюється плавно, дрібними кроками. На 9 бітах те саме повільне перекривання рукою дає лише кілька десятків можливих значень — у логу видно, що показник «стрибає» через кілька одиниць одразу, замість плавної зміни на одиницю.
Звідки береться LSB (крок кванта)
Формула кроку кванта: LSB = Vref / 2^N, де N — розрядність. При Vref ≈ 3.3 В: 12 біт → 3.3/4096 ≈ 0.805 мВ; 9 біт → 3.3/512 ≈ 6.45 мВ. Дві напруги, що відрізняються менше ніж на LSB, АЦП не розрізнить — вони закодуються однаковим числом.

Чому не завжди варто брати максимум біт
Більша розрядність не рятує від шуму самого сигналу (тремтіння значення з Кроку 1) — вона лише дрібніше ділить діапазон. Якщо шум датчика вже «більший» за LSB, зайві біти просто показують випадкові коливання останніх розрядів. Для боротьби з шумом потрібен інший інструмент — оверсемплінг (Крок 5).

Кожен окремий замір містить трохи шуму і помилку квантування. Якщо тримати сигнал незмінним і зробити багато замірів, їх середнє виявляється точнішим за будь-який окремий замір.

Чому усереднення працює
Шум АЦП переважно випадковий і симетричний навколо справжнього значення — то трохи вище, то трохи нижче. Якщо додати багато таких вимірів і поділити на їхню кількість, випадкові відхилення гасять одне одного, а справжнє значення «проступає» точніше. Це той самий принцип, що й у фотографії з довгою витримкою: багато кадрів складаються в один чіткіший.
Побічний ефект: «зайві» ефективні біти
Правило оверсемплінгу: усереднення 4^n замірів дає приблизно +n ефективних біт точності. У нашому прикладі 16 = 4², тобто ми «виграли» приблизно 2 додаткові ефективні біти над «сирим» 12-бітним значенням — платимо за це часом (16 замірів замість одного).

Порівняй із мультиметром
Постав мультиметр у режим вимірювання напруги (DC) між GPIO34 і GND. Порівняй його показ із обома стовпчиками в логу — calibrated і naive. Який ближче до показу мультиметра?
Звідки береться розходження
Формула (raw / 4095) × 3300 припускає, що опорна напруга рівно 3.3 В і що АЦП ідеально лінійний. У реальності живлення плати може бути 3.28–3.34 В, а АЦП ESP32 має відому нелінійність, особливо біля країв діапазону. adc_cali_raw_to_voltage() читає заводські калібрувальні коефіцієнти, «прошиті» в eFuse ще на виробництві саме для цього конкретного чипа, і враховує реальну форму характеристики — тому результат зазвичай ближчий до показу мультиметра, ніж «наївна» формула.
Правильна й неправильна формула — часта помилка
У «наївній» формулі завжди діли на максимальне значення поточної розрядності: для 12 біт це 4095, а не 65535 (це було б 16-бітне значення) і не 4096 (це кількість рівнів, а не максимальний індекс — рівні йдуть від 0 до 4095). Якщо змінив bitwidth, зміни й дільник у формулі.

// Модуль 3.1 — Крок 7: ФІНАЛ — неблокуючий сигналізатор темряви
#include <stdio.h>
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "driver/gpio.h"
#include "esp_adc/adc_oneshot.h"
#include "esp_adc/adc_cali.h"
#include "esp_adc/adc_cali_scheme.h"
#include "esp_timer.h"                 // esp_timer_get_time() — для неблокуючого розкладу читань
#include "esp_log.h"

#define ADC_UNIT       ADC_UNIT_1
#define ADC_CHANNEL    ADC_CHANNEL_6
#define LED_PIN        GPIO_NUM_5

#define SAMPLES            16          // оверсемплінг: скільки замірів усереднюємо за один цикл
#define SAMPLE_PERIOD_US   (50 * 1000) // період дискретизації: 50 мс = 20 Гц
#define THRESHOLD_ON_RAW   1500        // стає темно нижче цього "сирого" рівня
#define THRESHOLD_OFF_RAW  1800        // вважаємо "знову світло" вище цього рівня

static const char *TAG = "ADC_FINAL";

static int read_averaged(adc_oneshot_unit_handle_t handle)      // оверсемплінг проти шуму (Крок 5)
{
    long sum = 0;
    for (int i = 0; i < SAMPLES; i++) {
        int raw = 0;
        adc_oneshot_read(handle, ADC_CHANNEL, &raw);
        sum += raw;
    }
    return (int)(sum / SAMPLES);
}

void app_main(void)
{
    gpio_config_t led_conf = {                              // налаштування виходу LED
        .pin_bit_mask = 1ULL << LED_PIN,
        .mode = GPIO_MODE_OUTPUT,
    };
    gpio_config(&led_conf);

    adc_oneshot_unit_handle_t adc1_handle;                  // налаштування АЦП (Крок 1)
    adc_oneshot_unit_init_cfg_t init_config = { .unit_id = ADC_UNIT };
    adc_oneshot_new_unit(&init_config, &adc1_handle);

    adc_oneshot_chan_cfg_t chan_config = {
        .bitwidth = ADC_BITWIDTH_DEFAULT,
        .atten    = ADC_ATTEN_DB_12,
    };
    adc_oneshot_config_channel(adc1_handle, ADC_CHANNEL, &chan_config);

    adc_cali_handle_t cali_handle = NULL;                   // калібрування (Крок 6) — для друку вольтів у лог
    adc_cali_curve_fitting_config_t cali_config = {
        .unit_id = ADC_UNIT, .chan = ADC_CHANNEL,
        .atten = ADC_ATTEN_DB_12, .bitwidth = ADC_BITWIDTH_DEFAULT,
    };
    adc_cali_create_scheme_curve_fitting(&cali_config, &cali_handle);

    bool led_on = false;                // офіційний, підтверджений гістерезисом стан
    int64_t last_sample = 0;            // мітка часу останнього виміру (мкс)

    while (1) {
        int64_t now = esp_timer_get_time();

        if (now - last_sample >= SAMPLE_PERIOD_US) {   // неблокуюча дискретизація за розкладом
            last_sample = now;

            int level = read_averaged(adc1_handle);    // квантоване, усереднене значення освітленості

            int mv = 0;
            adc_cali_raw_to_voltage(cali_handle, level, &mv);

            // --- гістерезис: два різні пороги замість одного ---
            if (!led_on && level < THRESHOLD_ON_RAW) {
                led_on = true;                          // стало темно → вмикаємо
            } else if (led_on && level > THRESHOLD_OFF_RAW) {
                led_on = false;                         // стало досить світло → вимикаємо
            }
            gpio_set_level(LED_PIN, led_on);

            ESP_LOGI(TAG, "level=%4d (%d mV)   led=%s", level, mv, led_on ? "ON" : "off");
        }

        vTaskDelay(pdMS_TO_TICKS(5)); // невелика пауза — лишає час планувальнику FreeRTOS, не впливає на точність дискретизації
    }
}
⚠️ Часті помилки монтажу (з реального налагодження)
① Дільник переплутано місцями. Якщо LDR стоїть після резистора (ближче до GND), поведінка інвертується: на світлі напруга падає, а не росте. Перевір мультиметром: на яскравому світлі у вузлі GPIO34 має бути висока напруга (ближче до 3.3V).
② Немає точки з'єднання. LDR і резистор мають з'єднуватись саме у вузлі з дротом до GPIO34 — якщо на макетці ряд зсунутий на одну лунку, кола нема й adc_oneshot_read() дає або 0, або 4095 постійно.
③ Один поріг замість двох. Якщо порівнювати з одним порогом, а освітленість природно тремтить біля межі (шум АЦП + власне мерехтіння світла), LED почне «мигтіти» по кілька разів за секунду. Два пороги (THRESHOLD_ON_RAW < THRESHOLD_OFF_RAW) з проміжком-«мертвою зоною» вирішують це.
④ Забуто REQUIRES esp_adc у CMakeLists.txt — збірка впаде на етапі інклюдів, ще до будь-якого коду.
Чому гістерезис — це аналоговий аналог дебаунсу
У модулі про кнопки дребезг контактів прибирали часовим вікном (ігноруй події ближче ніж N мс). Тут шум навколо порогу прибираємо амплітудним вікном: замість однієї межі — дві, з проміжком між ними. Поки значення не вийшло за протилежний поріг, стан не змінюється. Це той самий принцип «не довіряй одиничному коливанню сигналу», тільки застосований до амплітуди, а не до часу.
Міні-експеримент: постав один поріг замість двох
Заміни обидва пороги на одне значення 1650 і плавно тримай долоню на межі тінь/світло над датчиком. Подивись, скільки разів клацає LED і скільки рядків level=... зі зміною стану з'являється в моніторі. Поверни два пороги — і повтори: клацання майже зникають.

Термістор NTC на ESP32: той самий АЦП, інша фізикаДРУГИЙ ДАТЧИК НА ОКРЕМОМУ КАНАЛІ ADC1 · ESP-IDF
У тебе в наборі є і фоторезистор, і термістор — тож зберемо обидва одночасно на двох каналах ADC1, у повноцінній робочій програмі: LDR керує сигналізатором темряви (з гістерезисом і калібруванням), а NTC паралельно друкує температуру, з перевіркою помилок читання на кожному кроці.
Дільник напруги з NTC-термістором — окремий канал ADC1

Термістор — не полярний компонент (як звичайний резистор, різниці між виводами немає). Схема — той самий дільник напруги, що й з LDR, але на іншому піні, щоб обидва датчики могли працювати паралельно: 3.3V → NTC → (вузол з ADC-піном) → резистор 10 кОм → GND. З ростом температури опір NTC падає — отже, напруга у вузлі зростає.

// Модуль 3.1 — Частина 5: LDR-сигналізатор + NTC, з повною обробкою помилок
#include <stdio.h>

#include <unistd.h>
#include <math.h>

#include "driver/gpio.h"
#include "esp_adc/adc_cali.h"
#include "esp_adc/adc_cali_scheme.h"
#include "esp_adc/adc_oneshot.h"
#include "esp_err.h"
#include "esp_log.h"
#include "esp_timer.h"
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "hal/adc_types.h"

#define LDR_UNIT       ADC_UNIT_1
#define LDR_CHANNEL    ADC_CHANNEL_5     // GPIO33
#define NTC_UNIT       ADC_UNIT_1
#define NTC_CHANNEL    ADC_CHANNEL_3     // GPIO39
#define LED_PIN        GPIO_NUM_5

#define SAMPLES                16
#define SAMPLE_PERIOD_US       (50 * 1000)
#define THRESHOLD_ON_RAW       1500
#define THRESHOLD_OFF_RAW      1800

#define ADC_MAX_RAW            4095
#define APPROX_ADC_FULL_MV     3300

/* NTC datasheet values:
 * R25      = 10 kohm +/-1%
 * B25/50   = 3950 K +/-1%
 *
 * Divider connection must match the DigiKey example:
 * 3.3 V -> NTC -> ADC node -> SERIES_R -> GND
 */
static const float SERIES_R_OHM = 10000.0f;
static const float NTC_R25_OHM  = 10000.0f;
static const float NTC_T25_C    = 25.0f;
static const float NTC_B25_50_K = 3950.0f;

static const char *TAG = "NTC";

static float raw_to_ntc_resistance_ohm(int raw)
{
    if (raw <= 0 || raw >= ADC_MAX_RAW) {
        return NAN;                       // захист від ділення на нуль і межових "сирих" значень
    }

    /* DigiKey divider formula:
     * R_NTC = R_series * (ADC_max / ADC_raw - 1)
     */
    return SERIES_R_OHM *
           ((float)ADC_MAX_RAW / (float)raw - 1.0f);
}

static float raw_to_temperature_c(int raw)
{
    const float r_ntc = raw_to_ntc_resistance_ohm(raw);

    if (!isfinite(r_ntc) || r_ntc <= 0.0f) {
        return NAN;                       // NAN з попередньої функції поширюємо далі, а не "тихо" рахуємо сміття
    }

    const float t25_k = NTC_T25_C + 273.15f;

    /* Beta equation:
     * 1/T = 1/T25 + ln(R/R25)/B
     */
    const float inverse_t =
        (1.0f / t25_k) +
        (logf(r_ntc / NTC_R25_OHM) / NTC_B25_50_K);

    if (!isfinite(inverse_t) || inverse_t <= 0.0f) {
        return NAN;
    }

    return (1.0f / inverse_t) - 273.15f;
}

static int read_averaged(adc_oneshot_unit_handle_t handle,
                         adc_channel_t channel)
{
    int64_t sum = 0;
    int valid_samples = 0;               // рахуємо лише вдалі заміри — не всі SAMPLES обов'язково пройдуть без помилок

    for (int i = 0; i < SAMPLES; i++) {
        int raw = 0;

        if (adc_oneshot_read(handle, channel, &raw) == ESP_OK) {
            sum += raw;
            valid_samples++;
        }
    }

    if (valid_samples == 0) {
        return -1;                        // сигналізуємо виклику: жодного вдалого виміру не було
    }

    return (int)(sum / valid_samples);
}

void app_main(void)
{
    gpio_config_t led_conf = {
        .pin_bit_mask = 1ULL << LED_PIN,
        .mode = GPIO_MODE_OUTPUT,
    };
    ESP_ERROR_CHECK(gpio_config(&led_conf));

    adc_oneshot_unit_handle_t adc1_handle = NULL;
    adc_oneshot_unit_init_cfg_t init_config = {
        .unit_id = LDR_UNIT,
    };
    ESP_ERROR_CHECK(adc_oneshot_new_unit(&init_config, &adc1_handle));

    adc_oneshot_chan_cfg_t chan_config = {
        .bitwidth = ADC_BITWIDTH_12,
        .atten = ADC_ATTEN_DB_12,
    };
    ESP_ERROR_CHECK(adc_oneshot_config_channel(     // один юніт ADC1 — два незалежно налаштовані канали
        adc1_handle, LDR_CHANNEL, &chan_config));
    ESP_ERROR_CHECK(adc_oneshot_config_channel(
        adc1_handle, NTC_CHANNEL, &chan_config));

    adc_cali_handle_t cali_handle = NULL;
    adc_cali_curve_fitting_config_t cali_config = {
        .unit_id = LDR_UNIT,
        .chan = LDR_CHANNEL,             // калібрування прив'язане саме до каналу LDR
        .atten = ADC_ATTEN_DB_12,
        .bitwidth = ADC_BITWIDTH_12,
    };

    const esp_err_t cali_ret =
        adc_cali_create_scheme_curve_fitting(&cali_config, &cali_handle);
    const bool calibration_available = (cali_ret == ESP_OK);

    if (!calibration_available) {
        ESP_LOGW(TAG,
                 "ADC factory calibration unavailable; "
                 "LDR voltage will be approximate");
    }

    bool led_on = false;
    int64_t last_sample = 0;

    while (true) {
        const int64_t now = esp_timer_get_time();

        if (now - last_sample >= SAMPLE_PERIOD_US) {   // неблокуюча дискретизація LDR за розкладом
            last_sample = now;

            const int level = read_averaged(adc1_handle, LDR_CHANNEL);

            if (level >= 0) {
                int voltage_mv =
                    (level * APPROX_ADC_FULL_MV) / ADC_MAX_RAW;   // "наївна" формула — запасний варіант

                if (calibration_available) {
                    int calibrated_mv = 0;
                    if (adc_cali_raw_to_voltage(
                            cali_handle, level, &calibrated_mv) == ESP_OK) {
                        voltage_mv = calibrated_mv;               // а тут — точне, якщо калібрування вдалося
                    }
                }

                if (!led_on && level < THRESHOLD_ON_RAW) {
                    led_on = true;
                } else if (led_on && level > THRESHOLD_OFF_RAW) {
                    led_on = false;
                }

                gpio_set_level(LED_PIN, led_on ? 1 : 0);

                ESP_LOGI(TAG,
                         "LDR=%4d (%d mV)\tLED=%s",
                         level,
                         voltage_mv,
                         led_on ? "ON" : "OFF");
            } else {
                ESP_LOGW(TAG, "Failed to read LDR ADC channel");   // АЦП повернув помилку — не тихо ігноруємо
            }
        }

        const int ntc_raw = read_averaged(adc1_handle, NTC_CHANNEL);  // NTC читаємо щоразу — без гейта за часом

        if (ntc_raw >= 0) {
            const float r_ntc = raw_to_ntc_resistance_ohm(ntc_raw);
            const float temp_c = raw_to_temperature_c(ntc_raw);

            if (isfinite(temp_c)) {
                ESP_LOGI(TAG,
                         "NTC=%4d\tR=%.1f ohm\tT=%.2f C",
                         ntc_raw,
                         r_ntc,
                         temp_c);
            } else {
                ESP_LOGW(TAG,
                         "Invalid NTC ADC value: raw=%d",
                         ntc_raw);
            }
        } else {
            ESP_LOGW(TAG, "Failed to read NTC ADC channel");
        }

        vTaskDelay(pdMS_TO_TICKS(500));    // темп циклу ~2 Гц — і LDR (гейт 50 мс), і NTC встигають щоразу
    }
}
Експеримент: подихай на термістор або притисни пальцем
Обережно затисни NTC між пальцями (або подихай на нього) і подивись, як зростає T=... у логу — з невеликою затримкою через теплову інерцію самого корпусу термістора. Одночасно прикрий LDR рукою — переконайся, що LED=ON і NTC=... друкуються в одному й тому самому циклі, незалежно одне від одного.
Чому тут з'явилися NAN і перевірки повернених кодів — це не «зайва обережність»
У Кроках 1-8 ми вважали, що adc_oneshot_read() завжди вдається, а raw завжди в «безпечному» діапазоні. У реальному пристрої це не гарантовано: АЦП може тимчасово повернути помилку (наприклад, при конфлікті ресурсу), а формула NTC SERIES_R_OHM * (ADC_MAX_RAW / raw - 1.0f) ділить на raw — якщо він випадково дорівнює 0, це ділення на нуль. raw_to_ntc_resistance_ohm() заздалегідь відсікає raw <= 0 і raw >= ADC_MAX_RAW, повертаючи спеціальне значення NAN ("не число"), яке потім перевіряється через isfinite() на кожному етапі — помилка не «губиться» посередині обчислень, а явно доходить до логу як ESP_LOGW.
Чому LDR і NTC читаються по-різному в цьому циклі
LDR обгорнутий у перевірку now - last_sample >= SAMPLE_PERIOD_US — це неблокуюча дискретизація за розкладом, як і в Кроці 7. NTC читається щоразу, без гейта: температура змінюється значно повільніше за освітленість, тож окремий розклад для неї не критичний, а vTaskDelay(pdMS_TO_TICKS(500)) наприкінці циклу й так тримає загальний темп ~2 рази на секунду для обох датчиків.

Чим це відрізняється від eFuse-калібрування ESP32
На ESP32 калібрувальні коефіцієнти для кожного конкретного чипа записані на заводі в eFuse (одноразово програмована пам'ять) — програма лише зчитує їх через adc_cali_create_scheme_curve_fitting(). На STM32 механізм інший: HAL_ADCEx_Calibration_Start() запускає внутрішню самодіагностику АЦП просто зараз, яка компенсує зсув нуля (offset) конкретного вимірювального тракту в поточних умовах (температура, напруга живлення). Це не заміна фізичної точності — це усунення систематичного зміщення показів прямо перед стартом роботи.
Чому на STM32 не треба обирати атенюацію
На платі Black Pill вивід VREF+ АЦП з'єднаний з VDD (3.3В) напряму на платі, тому весь діапазон 0–3.3В АЦП читає нативно, без додаткового підсилення/послаблення входу. Саме тому в CubeMX немає налаштування, аналогічного ADC_ATTEN_DB_12 з ESP-IDF, — весь трюк з атенюацією на ESP32 існував лише тому, що його внутрішній АЦП фізично обмежений діапазоном ~0–1.1В.
Переведення у вольти (формула, аналог "наївної" з частини А)
float voltage = (raw / 4095.0f) * 3.3f;   // VREF+ = VDD = 3.3В на Black Pill
printf("raw=%lu   voltage=%.3f V\r\n", raw, voltage);

/* USER CODE BEGIN 0 */
static uint32_t read_averaged(void)                 // оверсемплінг проти шуму
{
    uint32_t sum = 0;
    for (int i = 0; i < SAMPLES; i++) {
        HAL_ADC_Start(&hadc1);
        HAL_ADC_PollForConversion(&hadc1, HAL_MAX_DELAY);
        sum += HAL_ADC_GetValue(&hadc1);
    }
    return sum / SAMPLES;
}
/* USER CODE END 0 */

/* USER CODE BEGIN WHILE */
while (1)
{
    uint32_t now = HAL_GetTick();

    if (now - last_sample >= SAMPLE_PERIOD_MS) {     // неблокуюча дискретизація за розкладом
        last_sample = now;

        uint32_t level = read_averaged();            // квантоване, усереднене значення освітленості

        // --- гістерезис: два різні пороги замість одного ---
        if (!led_on && level < THRESHOLD_ON_RAW) {
            led_on = 1;                               // стало темно → вмикаємо
        } else if (led_on && level > THRESHOLD_OFF_RAW) {
            led_on = 0;                                // стало досить світло → вимикаємо
        }
        HAL_GPIO_WritePin(LED_PIN_GPIO_Port, LED_PIN_Pin, led_on ? GPIO_PIN_SET : GPIO_PIN_RESET);

        float voltage = (level / 4095.0f) * 3.3f;
        printf("level=%4lu (%.3f V)   led=%s\r\n", level, voltage, led_on ? "ON" : "off");
    }
    /* USER CODE END WHILE */

    /* USER CODE BEGIN 3 */
}
/* USER CODE END 3 */

① Забуто виклик HAL_ADCEx_Calibration_Start() перед циклом — покази будуть постійно трохи зміщені відносно реальної напруги.
② LED_PIN_Pin / LED_PIN_GPIO_Port не знайдено компілятором — ці імена генеруються лише якщо в CubeMX задано User Label для піна (Крок 11.3); без нього треба писати GPIOB, GPIO_PIN_0 напряму.
③ printf «мовчить» — переконайся, що _write() у syscalls.c справді перевизначений (Крок 12) і що в налаштуваннях проєкту увімкнено Use float with printf (Project → Properties → C/C++ Build → Settings → MCU Settings), інакше %.3f друкуватиме сміття або нулі.
④ Дільник переплутано місцями — та сама помилка, що й у частині А: перевір мультиметром, що на світлі напруга на PA0 зростає.
Що спільне, а що відрізняється порівняно з ESP-IDF
Спільне: сама структура алгоритму — оверсемплінг, гістерезис, неблокуюча дискретизація за міткою часу — жодних змін у логіці. Відрізняється: джерело мітки часу (HAL_GetTick() замість esp_timer_get_time(), мілісекунди замість мікросекунд), спосіб читання АЦП (HAL_ADC_Start/PollForConversion/GetValue замість одного adc_oneshot_read()), і те, що конфігурація периферії задається графічно в CubeMX, а не текстом у коді.

Термістор NTC на STM32F411ДРУГИЙ КАНАЛ ADC1 · STM32CubeIDE · CubeMX
Той самий термістор, що й у розділі 9 для ESP32, тепер на STM32F411. Додаємо другий аналоговий канал у CubeMX — плата читатиме LDR і NTC одночасно, як і на ESP32.
Дільник напруги з NTC — ще один канал ADC1 у CubeMX

Схема — той самий дільник напруги: 3V3 → NTC → (вузол з ADC-піном) → резистор 10 кОм → GND. Термістор не полярний — орієнтація виводів значення не має.

3V3 ───[ NTC термістор ]───┬─── PA1 (ADC1_IN1) │ [ 10 кОм ] │ GND
Вивід STM32F411Куди йдеУ CubeMX
PA1вузол дільника (NTC + 10 кОм)Analog → ADC1_IN1 (окремий від LDR на PA0/IN0)
Що змінити в CubeMX
У дереві Analog → ADC1 онови ще один чекбокс — IN1. Пін PA1 підсвітиться як ADC1_IN1. У вкладці Parameter Settings перейди в режим Scan Conversion Mode = Enabled (тепер каналів два) і у списку Rank впорядкуй, який канал читається першим (наприклад, IN0 = Rank 1, IN1 = Rank 2). Натисни Generate Code, щоб CubeMX оновив MX_ADC1_Init().
Навіщо Scan Mode. Поки був один канал (лише LDR), Scan Conversion Mode = Disabled було ок. Із двома каналами на одному АЦП потрібен сканувальний режим: HAL по черзі перемикає АЦП між IN0 і IN1 за порядком Rank, і кожен виклик HAL_ADC_Start() + HAL_ADC_PollForConversion() віддає значення наступного каналу в черзі.
💡 Код: читання двох каналів + переведення NTC у температуру
Мета

Прочитати обидва канали по черзі (LDR і NTC), і для NTC застосувати те саме рівняння Стейнхарта-Харта, що й на ESP32 — формула фізики не залежить від платформи.

Код · Core/Src/main.c
/* USER CODE BEGIN 0 */
#include <math.h>

const float SERIES_R  = 10000.0f;
const float NOMINAL_R = 10000.0f;
const float NOMINAL_T = 25.0f;
const float B_COEFF   = 3950.0f;

static float raw_to_temperature_c(uint32_t raw)          // та сама формула, що й на ESP32
{
    float r = SERIES_R * (4095.0f / raw - 1.0f);
    float steinhart = r / NOMINAL_R;
    steinhart = logf(steinhart);
    steinhart /= B_COEFF;
    steinhart += 1.0f / (NOMINAL_T + 273.15f);
    steinhart = 1.0f / steinhart;
    return steinhart - 273.15f;
}
/* USER CODE END 0 */

/* USER CODE BEGIN WHILE */
while (1)
{
    HAL_ADC_Start(&hadc1);
    HAL_ADC_PollForConversion(&hadc1, HAL_MAX_DELAY);
    uint32_t ldr_raw = HAL_ADC_GetValue(&hadc1);          // Rank 1 = IN0 (PA0, LDR)

    HAL_ADC_Start(&hadc1);
    HAL_ADC_PollForConversion(&hadc1, HAL_MAX_DELAY);
    uint32_t ntc_raw = HAL_ADC_GetValue(&hadc1);          // Rank 2 = IN1 (PA1, NTC)

    float temp_c = raw_to_temperature_c(ntc_raw);

    printf("ldr=%4lu   ntc=%4lu   temperature=%.2f C\r\n", ldr_raw, ntc_raw, temp_c);

    HAL_Delay(500);                                        // температура міняється повільно — 2 Гц достатньо
    /* USER CODE END WHILE */

    /* USER CODE BEGIN 3 */
}
/* USER CODE END 3 */
Чому два послідовні виклики HAL_ADC_Start(), а не один
У режимі Scan Conversion Mode кожен виклик HAL_ADC_Start() + HAL_ADC_PollForConversion() просуває АЦП до наступного каналу за Rank. Перший виклик у цьому циклі повертає значення з IN0 (LDR), другий — з IN1 (NTC). Порядок точно відповідає списку Rank, який задано в CubeMX.
Експеримент: подихай на термістор або притисни пальцем
Затисни NTC між пальцями (або подихай на нього) — і подивись, як зростає temperature=... у моніторі, з невеликою затримкою через теплову інерцію корпусу термістора.
Що спільне з ESP32, а що — ні
Формула Стейнхарта-Харта — ідентична на обох платформах: фізика термістора не залежить від MCU. Відрізняється лише спосіб отримати «сире» число з другого каналу: на ESP32 це окремий незалежний виклик adc_oneshot_read(handle, NTC_CHANNEL, &raw) для будь-якого каналу в будь-який момент; на STM32 у Scan Mode канали читаються по черзі, у порядку Rank, одним і тим самим HAL_ADC_GetValue().
